# Chapter 04: API Keys & Machine-to-Machine (M2M) Authentication

## 1. Machine-to-Machine (M2M) Communication & The Purpose of API Keys

In modern backend architectures, not all network interactions originate from human beings clicking buttons in a web browser. A substantial volume of network traffic consists of **Machine-to-Machine (M2M)** interactions: automated background jobs, CI/CD deployment pipelines, microservice-to-microservice synchronization, and integrations with third-party cloud services (such as OpenAI, Stripe, Twilio, or AWS).

```
   ┌───────────────┐
   │ React Browser │
   └───────┬───────┘
           │ 1. User Auth (Cookie/JWT)
           ▼
   ┌───────────────┐
   │ Your Backend  │
   └───────┬───────┘
           │ 2. Server-Held M2M API Key (`sk_live_...`)
           ▼
   ┌───────────────┐
   │ External AI   │ (e.g., OpenAI / Stripe API)
   │ Service       │
   └───────────────┘
```

### Why API Keys Exist:
1. **Programmatic Identity**: Unlike human users who enter passwords or complete MFA challenges, automated scripts require a reliable, long-lived, machine-readable credential.
2. **Billing & Quota Tracking**: External providers use API keys to measure consumption, invoice organizations, and enforce tier-based rate limits (e.g., 500 requests per minute).
3. **Decoupled Lifecycle**: API keys can be provisioned, rotated, scoped, or revoked without modifying user passwords or terminating interactive user sessions.

---

## 2. API Keys vs. User Authentication

A fundamental backend security rule is recognizing the boundary between **Client Identity** and **End-User Identity**:

```
┌─────────────────────────────────┬─────────────────────────────────┐
│     USER AUTHENTICATION         │      API KEY AUTHENTICATION     │
├─────────────────────────────────┼─────────────────────────────────┤
│ Identifies a specific human     │ Identifies an application,      │
│ individual (e.g., "Aminul").    │ client, project, or integration.│
├─────────────────────────────────┼─────────────────────────────────┤
│ Credentials entered on demand   │ Secret stored in server env     │
│ (passwords, MFA codes, biometrics) configuration or secret manager.│
├─────────────────────────────────┼─────────────────────────────────┤
│ Session expires quickly         │ Long-lived, designed for        │
│ (hours to days).                │ continuous background uptime.   │
├─────────────────────────────────┼─────────────────────────────────┤
│ Scoped to personal account.     │ Scoped to programmatic actions  │
│                                 │ (e.g., `invoices:read`).        │
└─────────────────────────────────┴─────────────────────────────────┘
```

### The Three-Tier Request Pattern:
When an authenticated user requests an AI-generated summary in an application:
1. **User Authentication**: The backend verifies the user's JWT or session cookie to confirm *who* is asking.
2. **User Authorization**: The backend checks if that user has remaining credits in their subscription.
3. **Server-Held API Key**: The backend uses its own private provider API key to communicate with the external AI API. The end-user **never sees or receives** the backend's secret API key.

## 3. High-Security Anatomy of an API Key

Modern production APIs (pioneered by Stripe, GitHub, and Slack) do not issue arbitrary, opaque UUIDs. They generate structured keys with explicit prefixes, cryptographically secure random entropy, and checksums.

```
       sk_live_51M0...92a1_kL90pX
       ── ──── ─────────── ──────
       │   │        │        │
       │   │        │        └─► Optional Checksum / Suffix
       │   │        └──────────► 256 bits of CSPRNG Entropy (Base62)
       │   └───────────────────► Environment: `live` vs `test`
       └───────────────────────► Key Type: `sk` (Secret Key) vs `pk` (Publishable Key)
```

### Anatomical Benefits:
1. **Immediate Context**: An engineer instantly recognizes what the key is for (`sk_live` = production secret, `pk_test` = safe test public key).
2. **Automated Secret Scanning**: Companies like GitHub and GitLab run regex scanners across public repositories. A standardized prefix allows platforms to detect leaked keys instantly and notify the provider for immediate revocation.
3. **High Entropy**: 256 bits of cryptographic entropy generated by a CSPRNG (`crypto.randomBytes(32)`) makes brute-forcing mathematically impossible.

## 4. Storage Architecture: Never Store Plaintext API Keys

Storing API keys as plaintext in a database is a critical security vulnerability. If an attacker gains read access to the database via SQL Injection or a compromised backup, every client integration is immediately breached.

```
                  RAW KEY CREATION (Only shown ONCE to user)
                    "sk_live_9a7b...c4"
                             │
                             ├────────────────────────► User copies to .env
                             │
                             ▼
                    Fast Cryptographic Hash
                       (SHA-256 / SHA-512)
                             │
                             ▼
                    "e3b0c44298fc1c14..."
                             │
                             ▼
                    DATABASE RECORD
                    ├── id: "key_101"
                    ├── prefix: "sk_live_9a7b..." (For identification UI)
                    ├── hashedKey: "e3b0c442..."  (For lookup & comparison)
                    ├── scopes: ["notes:read", "notes:write"]
                    ├── rateLimitRpm: 120
                    └── isActive: true
```

### Why SHA-256 is Appropriate for API Keys (Unlike Passwords):
* **Human Passwords**: Low entropy (short words, predictable phrases). Must use **slow, memory-hard hashing** (Argon2id, bcrypt) to thwart GPU dictionary attacks.
* **API Keys**: High entropy ($>256\text{ bits}$ of true randomness). Dictionary attacks are mathematically futile ($2^{256}$ possibilities). A fast cryptographic hash like **SHA-256** is ideal because it verifies incoming API requests in $<0.1\text{ ms}$ without bottlenecking high-throughput servers.

## 5. Express/Node.js Pseudocode: Complete API Key Management & Gatekeeper

The following TypeScript implementation demonstrates:
1. Generating a secure **Stripe-style API Key**.
2. **SHA-256 one-way hashing** for database storage.
3. Express **API Key Authentication Middleware** with **Scope Validation** and **Per-Key Rate Limiting**.

```typescript
// ==============================================================================
// Chapter 04: Production-Grade API Key Generation & Verification in Express
// ==============================================================================

import express, { Request, Response, NextFunction } from "express";
import crypto from "crypto";

const app = express();
app.use(express.json());

// ------------------------------------------------------------------------------
// 1. Data Models & In-Memory Store
// ------------------------------------------------------------------------------
export interface ApiKeyRecord {
  id: string;
  name: string;
  prefix: string;            // First 12 characters for UI identification (e.g. sk_live_abc1)
  hashedSecret: string;      // SHA-256 hash of the complete key
  scopes: string[];          // Allowed permissions, e.g. ["read:notes", "write:notes"]
  rateLimitRpm: number;      // Allowed requests per minute
  requestCount: number;      // Current window request counter
  windowStart: number;       // Timestamp of current rate-limit window
  isActive: boolean;
  createdAt: Date;
  expiresAt?: Date;
}

// In-Memory Database mapping hashedSecret -> ApiKeyRecord
const API_KEY_VAULT = new Map<string, ApiKeyRecord>();

// ------------------------------------------------------------------------------
// 2. Cryptographic API Key Generator
// ------------------------------------------------------------------------------
export class ApiKeyService {
  /**
   * Hashes raw API key string using SHA-256
   */
  public static hashKey(rawKey: string): string {
    return crypto.createHash("sha256").update(rawKey).digest("hex");
  }

  /**
   * Generates a high-entropy Stripe-style API key
   * Format: sk_{env}_{randomHex}
   */
  public static generateKey(
    name: string,
    scopes: string[],
    environment: "live" | "test" = "live",
    rateLimitRpm: number = 60
  ): { rawKey: string; record: ApiKeyRecord } {
    // 32 bytes = 256 bits of cryptographic entropy
    const randomEntropy = crypto.randomBytes(24).toString("hex");
    const rawKey = `sk_${environment}_${randomEntropy}`;

    const prefix = rawKey.substring(0, 14); // e.g., "sk_live_a1b2c3"
    const hashedSecret = this.hashKey(rawKey);

    const record: ApiKeyRecord = {
      id: "key_" + crypto.randomUUID().substring(0, 8),
      name,
      prefix,
      hashedSecret,
      scopes,
      rateLimitRpm,
      requestCount: 0,
      windowStart: Date.now(),
      isActive: true,
      createdAt: new Date()
    };

    // Store only the hash, never the plaintext key!
    API_KEY_VAULT.set(hashedSecret, record);

    return { rawKey, record };
  }
}

// Extend Request type to include the authenticated client API key
declare global {
  namespace Express {
    interface Request {
      apiKeyClient?: ApiKeyRecord;
    }
  }
}

// ------------------------------------------------------------------------------
// 3. API Key Authentication & Rate Limiting Middleware
// ------------------------------------------------------------------------------
export function authenticateApiKey(req: Request, res: Response, next: NextFunction): void {
  // Support both X-API-Key header and Authorization: Bearer <key>
  let rawKey: string | undefined = req.headers["x-api-key"] as string;

  if (!rawKey && req.headers.authorization?.startsWith("Bearer ")) {
    rawKey = req.headers.authorization.split(" ")[1];
  }

  if (!rawKey) {
    res.status(401).json({
      error: "UNAUTHORIZED",
      message: "Missing API key. Provide via 'X-API-Key' header or 'Authorization: Bearer <key>'."
    });
    return;
  }

  // Hash presented key to look up against stored records
  const presentedHash = ApiKeyService.hashKey(rawKey);
  const clientRecord = API_KEY_VAULT.get(presentedHash);

  if (!clientRecord || !clientRecord.isActive) {
    res.status(401).json({
      error: "UNAUTHORIZED",
      message: "Invalid, inactive, or revoked API key."
    });
    return;
  }

  // Check Expiration
  if (clientRecord.expiresAt && clientRecord.expiresAt.getTime() < Date.now()) {
    res.status(401).json({
      error: "UNAUTHORIZED",
      message: "API key has expired."
    });
    return;
  }

  // In-Memory Fixed-Window Rate Limiting Check
  const now = Date.now();
  if (now - clientRecord.windowStart > 60_000) {
    // Reset window
    clientRecord.windowStart = now;
    clientRecord.requestCount = 0;
  }

  clientRecord.requestCount += 1;
  if (clientRecord.requestCount > clientRecord.rateLimitRpm) {
    res.status(429).json({
      error: "TOO_MANY_REQUESTS",
      message: `Rate limit exceeded. Maximum ${clientRecord.rateLimitRpm} requests per minute.`,
      retryAfterSeconds: Math.ceil((60_000 - (now - clientRecord.windowStart)) / 1000)
    });
    return;
  }

  // Inject authenticated client record into request context
  req.apiKeyClient = clientRecord;
  next();
}

// ------------------------------------------------------------------------------
// 4. Scope Authorization Middleware
// ------------------------------------------------------------------------------
export function requireScopes(...requiredScopes: string[]) {
  return (req: Request, res: Response, next: NextFunction): void => {
    const client = req.apiKeyClient;

    if (!client) {
      res.status(401).json({ error: "UNAUTHORIZED", message: "API client context missing." });
      return;
    }

    const hasAllScopes = requiredScopes.every((scope) => client.scopes.includes(scope));
    if (!hasAllScopes) {
      res.status(403).json({
        error: "FORBIDDEN",
        message: `Forbidden. Client key lacks required scopes: [${requiredScopes.join(", ")}]. Active scopes: [${client.scopes.join(", ")}]`
      });
      return;
    }

    next();
  };
}

// ------------------------------------------------------------------------------
// 5. Routes: Key Provisioning & Scoped API Endpoints
// ------------------------------------------------------------------------------

// Key Generation Endpoint (Admin / Internal Portal)
app.post("/admin/api-keys", (req: Request, res: Response) => {
  const { name, scopes, rateLimitRpm } = req.body;

  const { rawKey, record } = ApiKeyService.generateKey(
    name || "External Service",
    scopes || ["notes:read"],
    "live",
    rateLimitRpm || 60
  );

  res.status(201).json({
    message: "API Key created successfully. WARNING: Copy the raw key now. It will NEVER be shown again.",
    apiKey: rawKey,
    keyMetadata: {
      id: record.id,
      prefix: record.prefix,
      scopes: record.scopes,
      rateLimitRpm: record.rateLimitRpm
    }
  });
});

// Protected API Route requiring `notes:read`
app.get(
  "/v1/notes",
  authenticateApiKey,
  requireScopes("notes:read"),
  (req: Request, res: Response) => {
    res.json({
      data: [
        { id: "note_1", title: "Quarterly Financials" },
        { id: "note_2", title: "API Documentation" }
      ],
      requestedBy: req.apiKeyClient?.name,
      requestsRemaining: (req.apiKeyClient?.rateLimitRpm || 0) - (req.apiKeyClient?.requestCount || 0)
    });
  }
);

// Protected API Route requiring `notes:write`
app.post(
  "/v1/notes",
  authenticateApiKey,
  requireScopes("notes:write"),
  (req: Request, res: Response) => {
    res.status(201).json({
      message: "Note successfully created via programmatic API key",
      client: req.apiKeyClient?.name
    });
  }
);

export default app;
```

## 6. Critical Operational Security Guidelines for API Keys

1. **Never Commit API Keys to Version Control**: Add `.env` to `.gitignore`. Use pre-commit hooks (such as `gitleaks` or `trufflehog`) to intercept committed keys before pushing to remote repositories.
2. **Never Pass Third-Party Private Keys to Frontend Apps**:
   * Bad: React app calls `https://api.openai.com/v1/chat` using `process.env.OPENAI_API_KEY`. (The key is embedded into public client-side JavaScript!).
   * Correct: React app calls `/api/generate` on your backend with its own user auth; your backend securely calls OpenAI using a server-side secret.
3. **Always Display Keys Exactly Once**: When a user creates an API key in your dashboard, render the plaintext key once upon creation and instruct them to copy it. Never show the full key again; only display the prefix (`sk_live_ab12...`).
