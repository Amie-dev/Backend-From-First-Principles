# Chapter 05: Delegated Access & Federation (OAuth 2.0 & OpenID Connect)

## 1. The Delegated Access Problem: Why Password Sharing Must Die

In the early days of the web, if a third-party service (such as a trip-planning application) wanted to integrate with your data (such as your Google Calendar), it presented you with a dialog asking:

> *"Please enter your Google email and password so we can check your calendar."*

```
                  THE CATASTROPHIC ANTI-PATTERN
┌────────────────┐      Sends Google Password      ┌────────────────┐
│   Trip App     │ ◄────────────────────────────── │   User Aminul  │
└───────┬────────┘                                 └────────────────┘
        │ Has FULL access to Gmail, Google Drive,
        │ YouTube, Billing, and Admin Settings!
        ▼
┌────────────────┐
│  Google Cloud  │
└────────────────┘
```

### The Fatal Flaws of Password Sharing:
1. **Excessive Privilege**: The third-party app receives unlimited access to everything associated with your account, not just the calendar.
2. **Revocation Impossibility**: You cannot revoke the trip app's access without changing your Google password, which breaks every other device and application you use.
3. **Secret Exposure**: The trip app must store your plaintext Google password in its own database, making it an attractive target for attackers.

**The Solution**: **Delegated Authorization** via **OAuth 2.0** and **Identity Federation** via **OpenID Connect (OIDC)**.

---

## 2. OAuth 2.0: The Four Core Roles

**OAuth 2.0** (RFC 6749) is an authorization framework that enables a third-party application to obtain limited access to an HTTP service on behalf of a resource owner.

```
┌─────────────────────────────────┬────────────────────────────────────────────────────────┐
│ ROLE                            │ RESPONSIBILITY & REAL-WORLD EXAMPLE                    │
├─────────────────────────────────┼────────────────────────────────────────────────────────┤
│ 1. Resource Owner               │ The entity capable of granting access (e.g. End User)  │
├─────────────────────────────────┼────────────────────────────────────────────────────────┤
│ 2. Client                       │ The application requesting access (e.g. TripApp.io)    │
├─────────────────────────────────┼────────────────────────────────────────────────────────┤
│ 3. Authorization Server         │ Issues tokens upon authenticating user (accounts.google)│
├─────────────────────────────────┼────────────────────────────────────────────────────────┤
│ 4. Resource Server              │ Hosts protected APIs (calendar.googleapis.com)         │
└─────────────────────────────────┴────────────────────────────────────────────────────────┘
```

## 3. The Modern Industry Standard: Authorization Code Flow with PKCE

Historically, OAuth 2.0 defined several "grants" (Implicit, Resource Owner Password Credentials, Client Credentials, Authorization Code).

> [!WARNING]
> * **The Implicit Flow is DEPRECATED**: It returned access tokens directly in URL hash fragments (`#access_token=...`), leaking tokens into browser history, web proxy logs, and referrer headers.
> * **Password Grant is DEPRECATED**: It still required passing plaintext passwords to third parties.
> * **Authorization Code Flow with PKCE (Proof Key for Code Exchange - RFC 7636)** is now the mandatory standard for both Single Page Applications (SPAs), Mobile apps, and Server-Side Web Apps.

### PKCE Mechanics: The Cryptographic Handshake
PKCE prevents **Authorization Code Interception Attacks** using dynamic ephemeral cryptography:
1. **Code Verifier**: A high-entropy cryptographic random string ($43\text{–}128\text{ characters}$) generated by the client:
   $$\text{code\_verifier} = \text{randomBytes}(32)$$
2. **Code Challenge**: The Base64URL-encoded SHA-256 hash of the code verifier:
   $$\text{code\_challenge} = \text{Base64URL}(\text{SHA-256}(\text{code\_verifier}))$$

```
Client (Trip App)                Auth Server (Google Auth)             Resource Server (Google Calendar)
      │                                       │                                       │
      │ ── 1. Redirect to /authorize ───────► │                                       │
      │    (client_id, scope, state,          │                                       │
      │     code_challenge, method=S256)      │                                       │
      │                                       │ (User logs in & clicks 'Consent')     │
      │ ◄─ 2. Redirect to /callback?code=XYZ ─│                                       │
      │                                       │                                       │
      │ ── 3. POST /token (Backend-to-Backend)│                                       │
      │    (code=XYZ, code_verifier) ───────► │                                       │
      │                                       │ (Verify SHA256(verifier) == challenge)│
      │ ◄─ 4. Returns AccessToken + IDToken ──│                                       │
      │                                                                               │
      │ ── 5. GET /v1/events (Authorization: Bearer <AccessToken>) ─────────────────► │
      │ ◄─ 6. 200 OK [Calendar Events JSON] ───────────────────────────────────────── │
```

### Protection Against CSRF: The `state` Parameter
Before redirecting to the Authorization Server, the client generates a unique cryptographically random `state` string stored in the user's session. When the provider redirects back with `?code=XYZ&state=ABC`, the client validates that `state` matches. If mismatched, the request is aborted to prevent login cross-site request forgery.

## 4. OpenID Connect (OIDC): The Identity Layer

A major historical misunderstanding was attempting to use OAuth 2.0 alone for user authentication.

$$\textbf{OAuth 2.0 is an AUTHORIZATION framework; it is NOT an authentication protocol.}$$

OAuth 2.0 answers: *"Can TripApp access Calendar API?"* It does **not** provide a standardized way to answer: *"Who is the logged-in user, what is their email, and what is their full name?"*

### Enter OpenID Connect (OIDC)
**OpenID Connect 1.0** is an identity layer built directly on top of OAuth 2.0. It standardizes identity exchange by introducing the **ID Token**.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                       OPENID CONNECT TOKEN TRIAD                            │
├───────────────────┬───────────────────────────────┬─────────────────────────┤
│ TOKEN             │ AUDIENCE / CONSUMER           │ PURPOSE                 │
├───────────────────┼───────────────────────────────┼─────────────────────────┤
│ **ID Token**      │ Your Client Backend/Frontend  │ Proves identity claims  │
│                   │ (Signed JWT)                  │ (sub, email, name)      │
├───────────────────┼───────────────────────────────┼─────────────────────────┤
│ **Access Token**  │ External Resource Server API  │ Grants API authorization│
│                   │ (Opaque or JWT)               │ to read/write resources │
├───────────────────┼───────────────────────────────┼─────────────────────────┤
│ **Refresh Token** │ Auth Server (`/token`)        │ Obtains fresh tokens    │
│                   │ (Opaque String)               │ without user prompt     │
└───────────────────┴───────────────────────────────┴─────────────────────────┘
```

### Standard OIDC Claims inside an ID Token:
```json
{
  "iss": "https://accounts.google.com",
  "sub": "109823091823091823091",
  "aud": "my-trip-app-client-id.apps.googleusercontent.com",
  "exp": 1700003600,
  "iat": 1700000000,
  "nonce": "n-0S6_WzA2Mj",
  "email": "aminul@example.com",
  "email_verified": true,
  "name": "Aminul Islam",
  "picture": "https://lh3.googleusercontent.com/a/..."
}
```

> [!IMPORTANT]
> **The Local Account Linking Pattern**:
> When a user signs in via *"Sign in with Google"*, your backend:
> 1. Validates the Google ID Token signature against Google's public JWKS keys.
> 2. Extracts `sub` (Google's immutable unique user ID) and `email`.
> 3. Queries your database: `SELECT * FROM users WHERE google_sub = ?`.
> 4. If missing, automatically creates a new local account.
> 5. **Crucial**: The backend establishes **its own local session or JWT** for your application. You do **not** forward Google's ID token on every internal API request.

## 5. Express/Node.js Pseudocode: Complete OIDC / OAuth 2.0 Client with PKCE

The following TypeScript implementation demonstrates an end-to-end OIDC workflow:
1. Generating a **PKCE Code Verifier & Challenge**.
2. Initiating the Google Auth redirect URL with `state` and `code_challenge`.
3. Handling the OAuth callback, validating the `state`, exchanging the `code` using `code_verifier`.
4. Decoding and validating the Google ID Token and establishing a local application session.

```typescript
// ==============================================================================
// Chapter 05: Complete OAuth 2.0 PKCE & OpenID Connect Flow in Node.js/Express
// ==============================================================================

import express, { Request, Response } from "express";
import crypto from "crypto";

const app = express();
app.use(express.json());

// Mock OAuth Configuration
const OAUTH_CONFIG = {
  clientId: "YOUR_GOOGLE_CLIENT_ID.apps.googleusercontent.com",
  clientSecret: "GOCSPX-your_google_client_secret",
  redirectUri: "http://localhost:3000/auth/callback/google",
  authorizationEndpoint: "https://accounts.google.com/o/oauth2/v2/auth",
  tokenEndpoint: "https://oauth2.googleapis.com/token",
  userInfoEndpoint: "https://openidconnect.googleapis.com/v1/userinfo"
};

// Ephemeral memory to track active login handshakes (In production, store in Redis)
interface LoginSessionState {
  codeVerifier: string;
  createdAt: number;
}
const stateStore = new Map<string, LoginSessionState>();

// ------------------------------------------------------------------------------
// 1. Cryptographic PKCE Utility Helpers
// ------------------------------------------------------------------------------
export class PkceHelper {
  /**
   * Generates a high-entropy code_verifier (43-128 characters)
   */
  public static generateVerifier(): string {
    return crypto.randomBytes(32).toString("base64url");
  }

  /**
   * Computes code_challenge = BASE64URL(SHA256(code_verifier))
   */
  public static computeChallenge(verifier: string): string {
    return crypto.createHash("sha256").update(verifier).digest("base64url");
  }
}

// ------------------------------------------------------------------------------
// 2. Step 1: Initiate OAuth Login -> Redirect User to Identity Provider
// ------------------------------------------------------------------------------
app.get("/auth/login/google", (_req: Request, res: Response) => {
  // 1. Generate PKCE verifier and challenge
  const codeVerifier = PkceHelper.generateVerifier();
  const codeChallenge = PkceHelper.computeChallenge(codeVerifier);

  // 2. Generate anti-CSRF state token
  const state = crypto.randomBytes(16).toString("hex");

  // 3. Persist state and verifier in temporary cache (keyed by state)
  stateStore.set(state, {
    codeVerifier,
    createdAt: Date.now()
  });

  // 4. Construct Authorization URL
  const queryParams = new URLSearchParams({
    client_id: OAUTH_CONFIG.clientId,
    redirect_uri: OAUTH_CONFIG.redirectUri,
    response_type: "code",
    scope: "openid email profile", // OIDC standard scopes
    state: state,
    code_challenge: codeChallenge,
    code_challenge_method: "S256",
    access_type: "offline",        // Request refresh token
    prompt: "consent"
  });

  const authorizationUrl = `${OAUTH_CONFIG.authorizationEndpoint}?${queryParams.toString()}`;

  // Redirect the browser to Google's consent screen
  res.redirect(authorizationUrl);
});

// ------------------------------------------------------------------------------
// 3. Step 2: Handle OAuth Callback & Token Exchange
// ------------------------------------------------------------------------------
app.get("/auth/callback/google", async (req: Request, res: Response): Promise<void> => {
  const { code, state, error } = req.query;

  // 1. Check for errors returned by Identity Provider
  if (error) {
    res.status(400).json({ error: "OIDC_PROVIDER_ERROR", details: error });
    return;
  }

  if (!code || !state || typeof state !== "string" || typeof code !== "string") {
    res.status(400).json({ error: "MALFORMED_CALLBACK", message: "Missing code or state parameter" });
    return;
  }

  // 2. Validate state token to defend against CSRF attacks
  const sessionState = stateStore.get(state);
  if (!sessionState) {
    res.status(403).json({ error: "CSRF_DETECTED", message: "Invalid or expired state parameter." });
    return;
  }

  // Consume and delete used state immediately
  stateStore.delete(state);

  const { codeVerifier } = sessionState;

  try {
    // 3. Backend-to-Backend Token Exchange (POST to /token)
    // In production, use native fetch or axios:
    // const tokenResponse = await fetch(OAUTH_CONFIG.tokenEndpoint, { ... });
    
    // Simulating token exchange payload:
    const tokenRequestBody = {
      client_id: OAUTH_CONFIG.clientId,
      client_secret: OAUTH_CONFIG.clientSecret,
      grant_type: "authorization_code",
      code: code,
      redirect_uri: OAUTH_CONFIG.redirectUri,
      code_verifier: codeVerifier // PKCE verification proof!
    };

    console.log("[OAUTH] Exchanging auth code with verifier:", tokenRequestBody);

    // Mocked Token Response from Identity Provider
    const mockTokenResponse = {
      access_token: "ya29.a0AfH6SM...",
      id_token: createMockIdToken("google_usr_9812", "aminul@example.com", "Aminul Islam"),
      expires_in: 3600,
      token_type: "Bearer",
      scope: "openid email profile"
    };

    // 4. Validate and Parse ID Token Claims
    const idTokenClaims = decodeJwtPayload(mockTokenResponse.id_token);

    // 5. Account Provisioning / Linking in Local Database
    const localUser = findOrCreateLocalUser({
      googleSubjectId: idTokenClaims.sub,
      email: idTokenClaims.email,
      name: idTokenClaims.name
    });

    // 6. Establish Local App Session (Set App Cookie or issue App JWT)
    res.setHeader("Set-Cookie", [
      `app_session=${localUser.localSessionId}; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=86400`
    ]);

    res.json({
      message: "Successfully authenticated via Google OpenID Connect!",
      user: {
        id: localUser.id,
        email: localUser.email,
        name: localUser.name
      }
    });
  } catch (err: any) {
    res.status(500).json({ error: "TOKEN_EXCHANGE_FAILED", message: err.message });
  }
});

// ------------------------------------------------------------------------------
// Helper Utility Functions
// ------------------------------------------------------------------------------
function decodeJwtPayload(token: string): any {
  const parts = token.split(".");
  if (parts.length !== 3) throw new Error("Invalid JWT");
  return JSON.parse(Buffer.from(parts[1], "base64url").toString("utf-8"));
}

function createMockIdToken(sub: string, email: string, name: string): string {
  const header = Buffer.from(JSON.stringify({ alg: "RS256", typ: "JWT" })).toString("base64url");
  const payload = Buffer.from(
    JSON.stringify({
      iss: "https://accounts.google.com",
      aud: OAUTH_CONFIG.clientId,
      sub,
      email,
      email_verified: true,
      name,
      iat: Math.floor(Date.now() / 1000),
      exp: Math.floor(Date.now() / 1000) + 3600
    })
  ).toString("base64url");
  const dummySignature = "mock_rsa_signature_verified_via_jwks";
  return `${header}.${payload}.${dummySignature}`;
}

function findOrCreateLocalUser(userData: { googleSubjectId: string; email: string; name: string }) {
  return {
    id: "usr_local_551",
    googleSubjectId: userData.googleSubjectId,
    email: userData.email,
    name: userData.name,
    localSessionId: "sess_" + crypto.randomBytes(16).toString("hex")
  };
}

export default app;
```

## 6. Summary Checklist for Delegated Auth

1. **Always use PKCE for all client types**: PKCE is not just for mobile apps; it defends confidential clients and SPAs against authorization code injection.
2. **Never accept an ID Token as an API Access Token**:
   * ID Token $\rightarrow$ Proves user identity to *your application*.
   * Access Token $\rightarrow$ Proves authorization to *the Resource Server API*.
3. **Always validate `state`**: Without a cryptographically unpredictable state check, attackers can force victims into linking attacker-controlled accounts (OAuth CSRF).
